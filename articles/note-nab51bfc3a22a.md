「もうプロンプトを打つな。ループを設計しろ」

2026年6月、たった数語のXのポストが開発者のタイムラインを二分しました。論点は「プロンプトを磨く」から「ループを設計する」へ。

私はちょうどその頃、自作ゲームの品質改善でAIに同じことをやらせていました。一手ずつ指示を出すのをやめて、**「停止条件を書いたファイル」を1枚渡しただけ**。AIはそれを読んで、約39周、自分でテストを回しながらゲームを作り込み続けました。

この記事は、こんな人向けに書いています。

- AIに長い作業を任せたいが、暴走やコストが怖い人

- 「ループエンジニアリング」という言葉を聞いたが、具体的に何をするのか知りたい人

- 個人開発でAIエージェントを実戦投入している人

📌 結論から言います。

**ループ設計の肝は「停止条件」と「検証ゲート」と「状態の外部化」の3つ。** そして最大の学びは、**ループは“実行”を自走させてくれるが、“方向”の正しさは最後まで人間が握る**、ということでした。実際、39周回して作り込んだその路線を、私は数日後に凍結しています。

その全部を、実物の設計ファイルを見せながら残します。

### なぜ今「プロンプト」ではなく「ループ」なのか

![](https://assets.st-note.com/production/uploads/images/290007781/rectangle_large_type_2_888bdd8649d94267cec1563dacf2f034.png)
ここ数年、AI開発の重心はずっと「外側」へ移動してきました。

- **〜2024：プロンプトエンジニアリング** … 1回の指示の質を最大化する

- **2025：コンテキストエンジニアリング** … 渡す情報・文脈の全体を設計する

- **2026初頭：ハーネスエンジニアリング** … 1体の実行環境・ツール・検証を設計する

- **2026.6〜：ループエンジニアリング** … 反復そのものを自走させ、その制御を設計する

ポイントは、各層は下を「置き換える」のではなく、上に「積み上がる」こと。プロンプトの技術は土台として効き続けます。

そしてもう一つ。**モデルの重みを変えなくても、外側の設計だけで成果は大きく動く**。だからこそ「外側」を設計する層が次々に立ち上がっているわけです。

ループエンジニアリングの定義を一言で言うと、こうなります。

> エージェントにプロンプトを打つ“自分自身”を、それを代行する仕組みに置き換えること。

これまでは、人間が一手ずつ道具を握り、1往復ごとの指示を磨いていました。これからは、**目的を一度定義すれば、完了条件を満たすまでAIが自走する**。人間が設計するのは「指示」ではなく、「指示を出し続ける仕組み」です。

### ループの正体は「観測→思考→行動→反省」の繰り返し

![](https://assets.st-note.com/production/uploads/images/290007783/rectangle_large_type_2_fbc355293a16879733720a9e5925414c.png)
Anthropicはエージェントを「LLMがツールを自律的に、ループの中で使うもの」と定義しています。そのループの中身は、突き詰めるとこの4ステップです。

1. **観測（Observe）** … 状態と結果を読む
2. **思考・判断（Decide）** … 次の一手を決める
3. **行動（Act）** … ツールを実行する
4. **反省・評価（Reflect）** … 結果を確かめる

これを「ゴール条件を満たすまで」繰り返す。設計の対象は、1往復の質ではなく**“繰り返し構造”そのもの**です。

そして一番大事なのが、**「どこで止めるか」を最初に決める**こと。完了・行き詰まり・予算超過のどれで止めるのかを、回し始める前に組み込んでおく。これがないと、ループは「開いた請求書」になります。

ここまでが理屈。ここからが、私が実際にやった話です。

### 【実録】自作ゲームの品質改善を、AIに39周“自走”させた

![](https://assets.st-note.com/production/uploads/images/290007788/rectangle_large_type_2_577f1c607e6afbe9a4d38420011c0436.png)
私はいま、ある
アクションゲームを個人開発しています。Godot 4.6製です。

目標は「Door Kickers 2 級のクオリティ」。賢い敵AI、計画的なテンポ、密度のあるレベル……要するに「ちゃんと面白い戦術ゲーム」です。

ここで最大の問題。**「DK2級のクオリティ」は主観**です。主観目標は、AIに「自走しろ」と言っても判定できません。「もう十分だ」を機械が決められないからです。

そこで私がやったのは、**主観目標を“機械判定できるチェックリスト”に変換する**こと。これがループ設計の出発点でした。

**ステップ1：停止条件を「1枚のファイル」に書く**

dk2_quality_bar.md というファイルを作り、その先頭にこう書きました。

> このファイルがループの唯一の停止条件。ループは毎周回これを読み、未チェックの項目を1つ潰す。## A. AUTO項目 が全て [x] になったら停止する。

そして本文を、こういうチェックリストにしました。

```
## A. AUTO項目（ループが自走・客観判定可）
### A1. 敵AIの戦術性
- [ ] 敵に視界コーン＋警戒3段階（緑=平常/黄=不審/赤=交戦）
- [ ] 検知→last_known_position 追跡（見失っても最終目撃地点へ）
- [ ] 警戒伝播：1体が赤化したら半径R内の敵へ無線伝播
...
```
ループの運用手順も、同じファイルに書き込みます。

1. AUTO項目を上から見て、最初の未チェック [ ] を1つ選ぶ
2. 実装する
3. **検証ゲートを通す**（後述）
4. 通ったら [x] にし、進捗ファイルに1行追記。通らなければ直してから次へ
5. 全 AUTO が [x] になったら停止

これで「観測（未チェック項目を読む）→思考（どう実装するか）→行動（実装）→反省（テストで確認）」の4ステップが、ファイルだけで回るようになりました。AIに毎回プロンプトを打つ私自身が、このファイルに置き換わったわけです。

**ステップ2：検証ゲート＝「自分で採点させない」**

ここが一番効きました。

各周回の終わりに、AIは必ず**ヘッドレスのスモークテスト**を走らせます。

```
godot --headless --path . --script res://tools/smoke_test.gd
```
出力に SMOKE_OK が出れば緑。中身はこんな判定です。

- パースエラー 0

- 全画面の起動でクラッシュ 0

- 全ミッション型の自動起動でクラッシュ 0

- マップ生成 40シードで fail=0

- その回で実装した項目の単体テストが PASS

これは、ループエンジニアリングで「マスト」とされる **Maker-Checker（生成役と検証役を分ける）** を、テストという形で持ち込んだものです。

Addy Osmaniの言葉が刺さります。

> 自分の宿題を採点するモデルは、優しすぎる。

生成したAIに「できた？」と聞くと、だいたい「できました」と言います。だから採点は別の仕組みに渡す。**テストが通らない限り、そのチェックは [x] にできない**。完了の判定を、AIの自己申告から機械の判定へ移したわけです。

これが必要だと痛感した事件があります。あるとき敵AIの項目について、AIは「全6項目を完了した」と報告してきました。チェックも [x] に並んでいる。ところが実際にコードを追うと、**肝心の「警戒伝播」がまったく未着手**だったのです。テストもまだ書かれていなかった。

つまり、自己申告だけ見ていたら「完了したつもり」で先に進んでいた。これに気づけたのは、各項目に「test_alert_propagation.gd が PASS していること」という機械判定を紐づけていたから。**“優しすぎる採点者”は、AIだけでなく、AIを信じきった私自身でもあった**わけです。停止条件は「AIが言ったか」ではなく「テストが通ったか」で書く。これは外せません。

結果、tools/tests/ 配下に単体テストが積み上がり、最終的に**150以上のアサーション**で品質を守る状態になりました。視界判定、警戒伝播、経路探索、味方AIの挙動確率……一つ実装するたびに、対応するテストが増えていきます。

**ステップ3：状態は「会話」ではなく「外部」に持つ**

長いループでよく壊れるのが「コンテキスト腐敗（context rot）」です。進捗も履歴も会話の中に積み上げると、長く回すほど文脈が膨張して、必要な情報を見つけられなくなる。

対策はシンプルで、**状態を会話の外の成果物に逃がす**こと。私の場合はこうでした。

- **進捗そのもの** … dk2_quality_bar.md のチェックボックス（どこまで終わったかが一目で分かる）

- **詳細ログ** … 進捗管理.md に1周ごと1行追記

- **コードの履歴** … git のコミット（多数）

これのいい所は、**AIがまっさらに再起動しても、外部の記録から「どこまで終わったか」を読み直して再開できる**こと。会話を途中で切っても、次のセッションがファイルを読めば続きから回せます。

git に状態を逃がしておく価値は、トラブったときに跳ね上がります。実際、ある周回でAIが味方AIのスクリプトを書き換える際、ファイルの読み書きが文字化けして**ソースの一部を巻き込んで壊す**事故がありました。普通なら数十分のロスです。でも各周回でコミットしていたので、git restore で1コマンド前の状態に戻し、その回の変更だけ再適用すれば済んだ。**「状態を外部に持つ」は、再開のためだけでなく、事故からの復旧のためでもある**——これは回してみて初めて体感しました。

**ステップ4：AUTO と HUMAN を分ける＝エスカレーション**

全部をAIに判定させるのは無理です。「テンポが反射でなく読みで勝てる遅さか」「敵が“賢い”と感じるか」「手触りがDK2級か」——こういう**主観評価はループでは判定できない**。

なので停止条件ファイルを2つに割りました。

- **A. AUTO項目** … ループが自走・客観判定可（テストで○×が付く）

- **B. HUMAN項目** … 私の実機プレイ判定が必須

そして運用手順に「全AUTOが終わったら、HUMAN項目を“要対応”リストへ吐き出して終了」と書いておく。これは、ループエンジニアリングでいう **エスカレーション（手に負えなければ人間へ引き継ぐ）** と **自律度の段階設計** そのものでした。

- L1：報告のみ（見つけて知らせる）

- L2：検証付き修正（直して、テストが通ったものだけ残す）← 私はここ

- L3：無人実行（最後まで人手を介さない）

私が選んだのは L2。「テストが通ったものだけ残す」。これなら回しっぱなしにしても、リグレッション（後退）が混入しません。

**結果：約39周回、敵AI7種・ダウン&救助・演出まで自走**

このループで実際に作り込まれたものを並べると、こうです。

- 敵戦術AI全7種（視界コーン／3段階警戒／last_known追跡／索敵／遮蔽利用／パトロール／**警戒伝播**）

- ダウン&救助システム（プレイヤーもダウン制、相棒AIが駆けつけて蘇生）

- 手触りの演出（マズルフラッシュ、被弾フラッシュ、画面遷移フェード、暖色の照明）

- 操作性のバグ修正（向きが追従しない、味方が密着しすぎる、扉が描画されない 等）

これを、私はほぼ「見ているだけ」で進めました。1項目ごとにテストが緑になり、チェックが [x] に変わり、コミットが積まれていく。約39周。これが「ループを設計する」の手触りでした。

### ループを「並列」で回す＝マルチAIエージェント

![](https://assets.st-note.com/production/uploads/images/290007794/rectangle_large_type_2_b93a7da221d2ae847b8d61534198c69f.png)
改善ループは、回すほど品質が上がります。だったら**複数のループを並列で走らせて量で押す**、というのが次の発想で、これがマルチAIエージェントの正体です。

私の今回の例は1本のループでしたが、設計を振り返ると、構成要素はそのまま並列化に流用できます。マルチエージェントの最小構成は、実は今回もう使っていた **Maker-Checker（生成役と検証役）** です。これを増やすと、こうなります。

- **オーケストレーター／ワーカー型** … 1体が仕事を分解・割当し、複数のワーカーが並行で実行する

- **役割分担** … Maker（作る）／Checker（テストする）／Reviewer（レビューする）を、責務が重ならないように定義する

ただ、並列化には固有の落とし穴があります。複数のループが**同じファイル・同じブランチ・同じ接続先に同時アクセスして衝突する**こと。これを避けるには、回す前に最低これだけ決めておきます。

- **ブランチ排他所有** … 各エージェントが触るブランチを分ける（git worktree が効く）

- **状態ファイル分離** … 進捗ファイルをループごとに別パスへ

- **役割分離** … Maker / Checker / Reviewer の責務を重複させない

- **統一 denylist** … 触ってはいけないファイル・コマンドを全員で共有

- **予算合算管理** … 各ループ単独ではなく、全体の予算を合算で監視

そして、一番大事な現実。**並列数の上限を決めるのは「ツール」ではなく、あなたの「レビュー帯域」**です。何体動かせるかではなく、**人間が結果を確認しきれる量**が天井になる。今回の私が1本に絞ったのも、結局「自分が1日に目を通せる差分量」がそこだったからでした。回す本数は、AIの能力ではなく自分の確認力で決まります。

### ループを支える6つの部品

![](https://assets.st-note.com/production/uploads/images/290007803/rectangle_large_type_2_7276a99987c03e8dfdb9afbb266908a3.png)
ここまでの話を部品に分解すると、ループは次の6つで構成されていました。今回の私の構成を当てはめると分かりやすいです。

- **記憶（状態の外部化）** … 停止条件ファイル・進捗ファイル・git履歴 ← 土台

- **知識（スキル）** … 守るべき規約や設計方針を別ファイルに書いて毎回読ませる

- **分業（Maker-Checker）** … 実装と、テストによる採点を分ける

- **自動化** … 「未チェック項目を1つ潰す」を毎周回トリガーで回す

- **隔離** … 並列時は作業領域を物理的に分ける（今回は1本なので省略）

- **連携（接続）** … Issueトラッカーやログへ手を伸ばす（MCP接続）

「記憶」を土台に、残りの部品が円環で噛み合い、その中をエージェントが自律的に巡回する。これがループの解剖図です。

### コスト爆発と、3つのハードガード

![](https://assets.st-note.com/production/uploads/images/290007807/rectangle_large_type_2_383ab3bd789c31dd1ba598c5014972db.png)
いい話だけではありません。ループは**回すほどトークンを食う**。一般に、通常チャット比でざっと4倍、マルチエージェントだと最大15倍とも言われます。あるテック企業は4か月で年間AI予算を使い切り、開発者1人あたり月1,500ドルに制限した、という報道もありました。

なので、回し始める前に最低3つの「ハードガード」を入れておくべきです。

1. **反復回数の上限** … ループ回数に天井を設け、無限反復を物理的に止める
2. **差分での停止** … 直近数回で diff が変わらなければ打ち切る（停滞検知）
3. **予算/金額の上限** … トークンやコストの上限に達したら止める

この3つが揃わなければ、それは「ループ」ではなく「開いた請求書」です。私の場合は停止条件ファイル（全項目チェックで終了）が事実上の天井になりましたが、これは自然に止まる設計になっていたから成立した話。常に出口を先に決めておくのが鉄則です。

### そして私は、その路線を「凍結」した
ここが一番リアルな学びです。

39周回して、テスト150以上、敵AIも演出も作り込んだ——その数日後、私はこの路線（リアルなDK2追従）を**凍結**しました。「2Dで本家を再現する」という方向そのものが力負けだと判断し、別のゲームシステムへ作り直したのです。

つまり、**ループは大量のアウトプットを正確に積み上げてくれたが、「そもそも何を作るべきか」が外れていたら、その成果ごと捨てることになる**。

ループエンジニアリングの記事や図解は、停止条件・検証ゲート・自律度といった「どう回すか」に集中しています。でも実戦で痛感したのは、その手前の話でした。

- ループが上手いのは「決めた方向に、速く・正確に・大量に進む」こと

- ループが決めてくれないのは「その方向が正しいか」

だから人間の仕事は、ループの中身を一手ずつ指示することではなく、**「正しい方向」と「止まる条件」を定義して、間違っていたら早めに方向ごと差し替えること**に移る。皮肉なことに、自走させればさせるほど、人間に残るのは「何を作るか」という一番むずかしい判断だけになります。

捨てたコードは無駄だったかというと、そうでもありません。テスト基盤も、共通化したジオメトリ処理も、停止条件ファイルという“回し方”そのものも、次の路線に持ち越せました。**ループの資産は、成果物よりも「回す仕組み」のほうに溜まる**、というのが正直な実感です。

ここから一つ実務的な教訓を引くなら、**「方向の検証」を「実装のループ」より前に、安く済ませておく**ことです。私の失敗は、方向（2Dで本家を再現できるか）に確信が持てないまま、実装のループを39周も回してしまったこと。回せば回すほど「ここまで作ったのだから」とサンクコストが効いて、方向転換が重くなります。

なので今は、本格的なループを回す前に、

- **小さく1〜2周だけ回して、方向そのものの“当たり”を見る**（プロトタイプ専用の使い捨てループ）

- そこで「これは伸びる」と人間が判断してから、停止条件ファイルを本気で書いて長く回す

という二段構えにしています。ループは強力なエンジンですが、エンジンを全開にする前に、行き先が正しいかをいちばん安いコストで確かめる。自走させられるようになったからこそ、**「回す前の判断」に時間を使うのが正解**になった、というのが今回の総括です。

### 実際、何を使って回すのか
「仕組みは分かったが、具体的に何で回すのか」という話。私が使ったのは Claude Code の自走ループ機能です。停止条件ファイルを渡して「これが空になるまで回して」と一度伝えるだけで、毎周回ファイルを読み直して1項目ずつ潰していきます。

同じことができるツールは増えています。Claude Code、OpenAI Codex、Cursor、Devin、OpenCode——いずれも「自動起動」「並行作業」「状態の外部化」といった、さきほどの6部品に近い公式の仕組みを備え始めています。どれを使うにせよ、**ツールに用意された機能で6部品を埋められるか**という目で選ぶと外しません。

適用先も、コードに限りません。

- **ソフトウェア開発** … CI修復、PR監視、コード品質の自律改善

- **コンテンツ運用** … 記事のリライト、レポートの定時生成

- **業務監視** … 定期的に繰り返す知的作業の見張りと対応

外部システムとの接続には MCP（Model Context Protocol）を使い、Issueトラッカーの読み取り・DB照会・ステージングAPI・Slack投稿までを束ねられます。投資の回収が速い順だと、GitHub → Linear / Jira → Slack → エラートラッカー、という体感です。まず「成否がコードで判定できる」開発タスクから始めるのが、いちばん事故りにくい入口でした。

---

### どこから始めるか：向いている仕事の見分け方
最後に、これから試す人向けに。ループに向く仕事は、次の3軸で見分けられます。

- **反復性** … 繰り返し発生する作業ほど、仕組み化の投資が回収できる

- **検証可能性** … 成否が機械で判定できる（テスト・計測がある）

- **経済価値** … 自動化の対象として割に合う

特に効くのが2つめの**検証可能性**です。私のゲームの例で言えば、「DK2級か」という主観は回せませんが、「smoke_test が緑か」「40シードで生成失敗ゼロか」は回せた。**主観目標を、いかに機械判定できる形に翻訳できるか**が、ループに乗るかどうかの分かれ目でした。

向いている条件を並べるとこうです。

- 強いテストスイートを持つコードベース

- 成否が機械でチェックできる作業

- ある程度の予算があるチーム（個人なら使用量を見られる状態）

- 「回している間に別のことができる」非同期前提

逆に、テストがない・成否が主観・1回しかやらない作業は、まだ手で回したほうが速いです。

---

### まとめ：7つの要点
1. レバレッジは「指示」から「設計」へ移った
2. ループ＝観測→思考→行動→反省 を、停止条件まで自走させる
3. 生成役と検証役を分ける（テストを採点役にする＝Maker-Checker）
4. 状態は会話ではなく、外部（ファイル／git）に持つ
5. 3つのハードガードなしに回さない（回数・差分・予算）
6. 反復性 × 検証可能性 × 経済価値 で対象を選ぶ
7. 自律度は L1 → L2 → L3 と段階的に上げる

そして、これに私自身の8つめを足すなら——

**ループは「実行」を自走させてくれるが、「方向」の正しさは最後まで人間が握る。** 39周回して凍結した私からの、いちばん正直な学びです。

「プロンプトを打つ人」から、「ループを設計する人」へ。やってみると、面倒な作業が減る代わりに、人間に残るのは一番おもしろい判断だけになります。悪くない移行だと思っています。
