### 全ステージ、自分より先にクリアされた

![](https://assets.st-note.com/production/uploads/images/285135060/rectangle_large_type_2_aaecb15c729dbaed2842037dd9620fe3.png)
個人でスマホゲームを開発しています。
公開前のタイトルです。

ステージ構成がある程度固まってきたころ、こんな問題に直面しました。

「このステージ、本当に解けるのか」を確認するのが、想像以上に大変だったんです。

10ステージ作った。全部クリア可能にしたい。でも自分でプレイするたびに詰まる。
「難しいのか、それとも設計が壊れているのか」の判断が、プレイするたびに混在します。

作者は解法を知っているので、難易度の感覚もズレます。
「これ難しい」と感じても、「手順を知っていれば解けるから問題ない」と判断を誤る。
逆に「簡単すぎる」と思っていたステージが、実は根本から成立していなかったということもありえます。

そこで考えた解決策が、**攻略ボットを書く**ことでした。

ゲームの物理演算をNode.jsで走らせて、「このステージの解法を実行するボット」を書く。
ボットがクリアできれば「理論上は解ける」確認が取れます。
ボットがFAILすれば、ステージ設計か物理実装のどちらかにバグがある。

実装した結果、npm run sim を実行すると全10ステージの検証が数秒で終わる環境ができました。
人間が初プレイする前に、ボットが全ステージを先にクリアしています。

この記事は、こんな人向けです。

- 個人でゲームを作っていて、ステージの検証に手間取っている人

- 「ゲームのテストってどうするの？」と思っているエンジニア

- ヘッドレス実行でシステムを検証する考え方に興味がある人

読み終わると、物理ゲームのステージをボットで自動検証する仕組みの作り方と、ボットが回帰テストとして機能するという発見が持ち帰れます。

なお、記事内で開発中のゲームの詳細（タイトル・コンセプト・固有のゲームメカニクス）は伏せています。公開に合わせて別途紹介する予定です。

### なぜゲームのステージ検証が難しいのか

![](https://assets.st-note.com/production/uploads/images/285135082/rectangle_large_type_2_f961d3f6d2143771dfd2bbba3740cfbb.png)
「ゲームのテストってそんなに大変？」と最初は思っていました。

問題はステージ設計の細かいバランスにあります。
数値が少しずれるだけで「見た目上は解けそう、でも物理的には届かない」状態になります。

**「2px足りない」は見えない**

たとえば足場の配置を考えます。

プレイヤーがある足場からジャンプして次の足場に着地するとき、「足場の幅が何px必要か」を正確に計算するのは実は難しいです。ジャンプの放物線、速度の減衰、着地判定のしきい値。これらが組み合わさると、グリッドエディタ上では届いて見えるのに、物理演算上では2px足りない、というケースが発生します。

人間がプレイして気づくのはほぼ不可能です。
「なんかここ着地が難しいな」「自分の操作のせいかな」という感覚で終わります。
設計が壊れているのに、プレイテストでは「難しいだけ」と混同してしまう。

**「難しい」と「壊れている」の区別がつかない**

もっと根本的な問題として、**作者がテストプレイすると客観性がない**というのがあります。

解法を知っていると「ちゃんと解けた」を確認するプレイになります。
「初見で解けるか」「そもそも解けるか」の確認にならない。

難易度を調整しようとしたとき、「この変更でステージが成立しなくなっていないか」を確認するのも大変です。
変更前後でプレイして比べる。でも記憶があるので比較がフェアにならない。

「プレイテストをほかの人に頼む」という選択肢もありますが、個人開発の序盤はそれも難しい。
知人に頼むと「難しかった」「楽しかった」程度のフィードバックしか得られないことも多い。
「このステージは物理的に成立しているか」という問いは、テストプレイヤーに尋ねても答えが出ません。

そもそも「成立しているかどうかが不明なステージ」を人に渡すのも気が引けます。
壊れているステージを人にプレイさせてしまうと、そのフィードバックは混乱したものになります。
「なんか詰まったけど自分が下手なのかも」と思われたまま終わる可能性もある。

**まず「成立している」を証明してから、人に渡す。**
この順番を作るためにも、ボットが必要でした。

この2つの問題を同時に解決するのが、攻略ボットでした。

### 設計：ゲームエンジンをNode.jsに持ち込む

![](https://assets.st-note.com/production/uploads/images/285135100/rectangle_large_type_2_3e3590db331bce0d40a7f79537e23ae2.png)
ゲーム本体はブラウザで動くTypeScript製です。Vite + TypeScriptで実装していて、Canvas描画、サウンド、UI周りが乗っています。

このゲームエンジン全体をNode.jsで動かすのは大変ですし、テストに必要な部分はもっと絞られています。
必要なのは「物理演算」だけです。座標計算、衝突判定、グリッドデータ。これだけあれば、ステージが解けるかどうかの検証はできます。

物理演算のコア部分（速度計算、衝突判定、ステージのグリッドデータ）を、ゲームエンジン側から切り出して、Node.jsのシミュレーション環境でも動かせるようにしました。

scripts/sim.ts というファイルが本体です。構成はざっくりこうなっています。

```
// 物理コンテキスト（ゲームエンジンから切り出し）
interface PhysicsContext {
  position: Vector2;
  velocity: Vector2;
  onGround: boolean;
  facing: "left" | "right";
}

// ステージ定義
interface Stage {
  id: number;
  grid: number[][];   // タイルの配置データ
  spawnX: number;
  spawnY: number;
  goalX: number;
  goalY: number;
}

// ボットの「思考」インターフェース
type BotInput = {
  left: boolean;
  right: boolean;
  jump: boolean;
};

type Bot = (ctx: PhysicsContext, frame: number) => BotInput;
```
あとは各ステージに対応する Bot 関数を書くだけです。
「フレーム12まで右を押して、フレーム13でジャンプ」という形で、1フレームごとの入力を時系列で記述します。

```
const bot_stage1: Bot = (_ctx, frame) => ({
  left: false,
  right: frame ボット関数を書くとき、設計者は「このステージはどう解くのか」を数値で考えなければなりません。
「フレーム何番でジャンプするか」「助走は何フレームか」。
これが思いの外、ステージ設計の精度を上げる副作用を持っていました。後述します。

これを物理ループに通して、最大600フレーム（10秒）以内にゴール座標に到達すればPASS、しなければFAILです。

```
$ npm run sim

Stage 01: PASS  (goal reached at frame 87)
Stage 02: PASS  (goal reached at frame 142)
Stage 03: PASS  (goal reached at frame 201)
...
Stage 10: PASS  (goal reached at frame 389)

10/10 passed in 94ms
```
全10ステージの実行時間は100ms以下。
コードを変更するたびにこれを走らせます。

### 実装してすぐ、2ステージでFAILした

![](https://assets.st-note.com/production/uploads/images/285135118/rectangle_large_type_2_a9ce17d418a8b1a381ee131269e71748.png)
simを組んで走らせてみると、最初から10/10にはなりませんでした。
2ステージでFAILが出ました。しかも物理実装のバグでした。

**バグ1：接地判定の毎フレーム振動**

最初のFAILの原因は、着地直後に onGround フラグが true/false を毎フレーム交互に繰り返すバグでした。

ゲームプレイ上はほぼ気づきません。描画は問題ないし、「なんかたまに操作がおかしい」くらいです。
でもボットにとっては致命的です。「地面に立っているかどうか」が不安定だと、ジャンプのタイミングが1フレームずれるだけで全然違う場所に行ってしまいます。

原因は衝突解決のコードが、着地後も毎フレーム微量にプレイヤーを上に押し戻していたことです。
押し戻されて浮く → 着地判定が外れる → また着地 → また押し戻し、のループ。

修正は簡単でした。接地判定の更新タイミングを、衝突解決処理の後に移動するだけ。
でもこのバグは、simがなければずっと気づかなかったかもしれません。
「たまに操作がおかしい」の原因を、プレイしながら特定するのは難しい。

トレースログを見れば原因は一目瞭然でした。

```
[frame 022] pos=(60.0, 112.0) vel=(3.5, 0.0) onGround=true
[frame 023] pos=(63.5, 110.8) vel=(3.5, 1.2) onGround=false  ← 浮いた
[frame 024] pos=(67.0, 112.0) vel=(3.5, 0.0) onGround=true   ← また着地
[frame 025] pos=(70.5, 110.8) vel=(3.5, 1.2) onGround=false  ← また浮く
```
地面に立っているのに毎フレーム微量に上に押し上げられて、着地 → 浮く → 着地を繰り返している。
人間の目には止まって見えますが、物理内部では振動していた。
simのトレースがなければ、この状態を可視化することすら難しかったと思います。

**バグ2：コーナークリップ後のテレポート先が壁の内部**

2件目はコーナー処理のバグです。

壁の角スレスレを通過したとき、衝突解決がプレイヤーを「壁から押し出す方向」に動かします。
このとき「押し出し先の座標」を計算するロジックが間違っていて、別の壁の内側に入ってしまっていました。

人間のプレイではほぼ発生しない状況（ピクセル単位のコーナー）なので、ゲームプレイ中はまず気づきません。
でもボットのトレースログには「座標が一瞬おかしな値を経由する」のがはっきり出ます。

```
[frame 034] pos=(124.0, 88.0) vel=(4.2, -6.1) onGround=false
[frame 035] pos=(128.2, 81.9) vel=(4.2, -6.1) onGround=false
[frame 036] pos=(132.4, 91.2) vel=(0.0, 0.0)  onGround=false  ← 座標が跳んでいる
[frame 037] pos=(132.4, 91.2) vel=(0.0, 0.0)  onGround=false  ← 止まった（壁の中）
```
修正に10行かかりませんでした。

### ステージ設計の破綻も大量に検出された

![](https://assets.st-note.com/production/uploads/images/285135156/rectangle_large_type_2_c7d8a4916bd99337a21c71124f8d73e6.png)
物理バグの修正後、2つのFAILがPASSになりました。
でもその後、ステージを追加・修正するたびにsimを走らせると、ステージ設計側の問題が多数出てきました。

- 「助走が2マス足りない」

- 「特定の足場の着地判定が厳しすぎて、見た目では届くのに物理上では届かない」

- 「連続する足場の間隔が詰めすぎていて、最速で移動すると次の段差で詰まる」

全部「グリッドエディタで直感的に配置した結果、物理との齟齬が生じた」というパターンです。

グリッドエディタは視覚的にタイルを置けるので設計は楽ですが、「実際の物理挙動とズレた感覚」で置きがちです。
足場の幅を1タイル短くした、壁の高さを1タイル増やした。それだけで到達不可能になる。

ここで気づいたのが、前述した「ボット関数を書くと設計意図が明文化される」という副産物です。

ボット関数を書こうとして、「このステージどう解くんだっけ」と止まる瞬間がありました。
設計した本人が解法をすぐに言語化できない。
これは設計が「なんとなく解けそう」という曖昧な状態のまま置かれていたサインでした。

解法をフレーム単位のコードとして書くことで、「このステージの想定解はこれ」が確定します。
ボットを書けないステージは設計が固まっていないステージです。

これを全部、人間のプレイテストで発見しようとすると途方もない手間です。
simはコードの変更のたびに数秒で洗い直してくれます。

### 最大の収穫：操作仕様変更の回帰テスト

![](https://assets.st-note.com/production/uploads/images/285135182/rectangle_large_type_2_6a657fc4792ada9ce5580f4757a118f3.png)
一番価値を感じたのは、**操作仕様を変更したときの影響確認**としてでした。

**変更したら10/10 → 8/10 になった**

ステージの難易度調整のため、特定の操作の入力受付フレームを変更しました。
プレイヤーが「意図した操作」をしやすくなるための改善です。

変更後に npm run sim を走らせると：

```
Stage 01: PASS
Stage 02: PASS
Stage 03: PASS
Stage 04: PASS
Stage 05: FAIL  ← 変更前はPASS
Stage 06: FAIL  ← 変更前はPASS
Stage 07: PASS
Stage 08: PASS
Stage 09: PASS
Stage 10: PASS

8/10 passed
```
「直感的な操作にするための変更が、2ステージのクリアルートを壊していた」。

人間のプレイテストだけでこれを確認しようとすると、「難易度が変わったのか、仕様変更で壊れたのか」の区別が難しいです。
simは数値で「8ステージしか成立しない状態になった」と教えてくれました。

**操作仕様を再設計してsimが証明した**

8/10になった原因を追って、操作仕様を再設計しました。
「素早い入力は向き転換、押し続けると別の動作に移行する」という意図の分離です。

設計後、simを走らせて10/10に戻ることを確認。
そこで初めて人間のプレイテストに渡しました。

「simが通っていないステージを人に渡しても、フィードバックが『壊れているかどうか』に終始する」

難易度・操作感・楽しさを聞きたいなら、まずsimで「成立している」を証明する。
この順番が定まったことが、開発の流れを変えました。

### sim導入前に検討して却下した方法
この手法に至る前に、別のアプローチも考えました。

**単体テストを書く**

最初に思い浮かんだのは「物理関数の単体テストを書く」でした。
Jestで updateVelocity() や resolveCollision() を個別にテストする方法です。

でも、これではステージの「クリア可能性」は確認できません。
各関数が正しく動いていても、組み合わさったときにステージが解けないケースは普通に起きます。
しかも「ステージ設計側の問題」は、物理関数のテストでは絶対に検出できません。

テストの対象は「ロジック」ではなく「ステージを通して解けるかどうか」でした。
E2Eに近い粒度が必要だった。

**ブラウザのE2Eテストを使う**

次に考えたのが PlaywrightでブラウザをヘッドレスE2Eテストする方法です。

これも却下しました。理由は2つ。

1つ目：ブラウザを立ち上げる起動コストが重い。
全ステージを毎回コード変更のたびに走らせるには、秒単位で終わる必要があります。
ブラウザ起動 + 描画 + 実際のゲーム時間待ち、ではとても無理です。

2つ目：ゲームのフレームレートが実時間に依存してしまう。
ブラウザ上でゲームを動かすと、描画とゲームループが結びついていて、実際の時間が流れます。
10秒かかるステージは10秒待つことになる。10ステージで100秒。

物理演算だけを切り出してNode.jsで走らせれば、時間の制約から解放されます。
600フレーム（ゲーム内10秒）の計算が、現実では数msで終わります。

### ボットは「可能性」しか証明できない
ここまで読むと「simがあれば人間プレイテストは不要では？」と思うかもしれません。

違います。

ボットはクリア「可能性」を証明するだけです。**「執行難度」は測れません。**

simを通過した後、実際に人間にプレイしてもらったところ、あるステージで詰まりました。
「理論上は解ける、でもそのルートを人間が実行するのが難しすぎる」という状態でした。

ボットは精確なフレーム入力を誤差なく実行できます。人間にはそれができない。

また、「発見性」も測れません。
「このルートに気づけるか」という発見の楽しさは、ボットには関係がありません。
ボットは解法を与えられたうえで、実行可能かどうかを確認するだけです。

なので現在は以下の使い分けをしています。

**確認したいこと** | **手段**

- このステージは理論上解けるか : sim（ステージ変更のたびに必ず走らせる）

- 難しすぎないか・楽しいか : 人間プレイテスト（sim通過後にのみ実施）

- 操作仕様変更で何か壊れていないか : sim（変更後に即座に走らせる）

- 初見で解法に気づけるか : 人間プレイテスト（解法を知らない人限定）

simは「クリア可能性の継続検証」、人間プレイテストは「体験品質の評価」。
この分業が定まると、どちらの作業も目的が明確になります。

### 他のゲームやシステムへの応用
この手法はゲーム開発特有ではありません。

「システムの仕様をヘッドレス実行でテストする」という構造は、Webアプリのシナリオテストやバッチ処理の検証と本質的に同じです。

ゲームの場合は物理シミュレーションですが、APIフローなら「シナリオスクリプト」、フォームのバリデーションなら「入力パターン一覧」に置き換えられます。

**この手法が有効なケースの共通点**

sim方式が特に有効なのは、こういうケースです。

**「処理が正しく動くか」ではなく「目標に到達できるか」を確認したい。**

単体テストは「関数が正しい値を返すか」を確認します。
simが確認するのは「入力を与え続けたとき、最終的に期待する状態に達するか」です。
これはゲームのクリアだけでなく、「ECサイトの購入フローが最後まで完走できるか」「バッチが全レコードを処理し終えるか」にも当てはまります。

**変更のたびに既存の「到達可能性」が壊れていないか回帰確認したい。**

ゲームでは「操作仕様を変えたらステージが解けなくなった」でした。
Webアプリなら「UIを改修したら既存のユーザーフローがどこかで詰まるようになった」に相当します。
「到達可能性」の継続的な確認は、ゲームに限らず必要な視点です。

ゲーム固有の面白さは、**ボット関数を書くとき、設計者が解法を明文化しなければならない**という副産物です。

```
const bot_stage5: Bot = (_ctx, frame) => ({
  right: frame = 20 && frame このコードを書くとき、「ステージ5はどう解くのか」を数値レベルで考えます。
「なんとなく解けた」ではなく「フレーム14でジャンプする」まで落とし込む。

あいまいな設計意図をコードに落とすことで、矛盾や不整合が見えやすくなります。
「解法を書こうとしたら書けなかった」は、設計が固まっていないサインです。

### まとめ
個人ゲーム開発に攻略ボット（シミュレーション）を導入した話をまとめます。

- 「壊れているのか難しいのか」は人間のプレイテストだけでは判断できない

- 物理演算をNode.jsに持ち込んで Bot 関数を書けば、100ms以下でPASS/FAILが出る

- 実装直後に接地判定バグとコーナークリップバグを発見できた

- ステージ設計の不備（2px足りない、助走距離不足）も多数検出できた

- 操作仕様を変更したとき、10/10 → 8/10 になったことをsimが即座に検出できた

- ボット関数を書くことで「解法の明文化」という副産物が得られた

- ボットは「クリア可能性」の証明、人間プレイテストは「体験品質の評価」と役割を分ける

**この手法で変わったこと**

導入前は「コードを変えたら一通り自分でプレイして確認する」というフローでした。
確認に10〜15分かかる。集中してコードを書いているときにそれをやると、開発の流れが止まります。
結果として「あとで確認する」が増えて、複数ステージに問題を溜めてしまうことがありました。

simを入れてからは「変えたら即 npm run sim」の習慣になりました。
10秒で終わるので、確認を先延ばしにする理由がない。
問題を小さいうちに潰せるようになりました。

**個人開発で「質を担保する仕組み」を持つ**

個人開発は、チームに比べてレビューもQAも手薄になりがちです。
だからこそ「自分でしか確認できない部分」を自動化できると、精神的な余裕が変わります。

ゲームの物理はsimが見てくれる。だから自分は設計とゲームとしての体験に集中できる。
この分業が、個人開発の継続に効いています。

ゲームを作っている方には直接使えますし、「仕様通りに動くかをヘッドレスで確認したい」あらゆる場面に応用できる考え方です。

ゲーム本体の公開に合わせて、実装の詳細と全ステージのボット実装も公開する予定です。
