そしてその中で、味方AIが勝手にドアを開けて、寝ていた敵を起こしていました。

これは私が「そう動け」と細かく命じた結果ではありません。

**内部メーターが上がった結果、確率的にやらかした**だけです。

この記事は、こんな人に向けて書いています。

- ゲームの「AIキャラ」を、乱数の突然死ではなく"読めるクセ"として設計したい人

読み終わると、**FSM＋2メーターで「憎めないポンコツ」を確率設計する**考え方が手に入ります。

そして、仕様書からAIにゲームを実装させるときの流れと、GDScript特有の地雷の避け方が分かります。

### 敵じゃなくて「味方」が一番危ない、という反転

![](https://assets.st-note.com/production/uploads/images/294114122/rectangle_large_type_2_2d9b467f20acb05d5a881b7a70e5eab1.png)
まず、このゲームのコンセプトを話させてください。

普通の見下ろし型シューターだと、危ないのは「敵」です。

でも私が作りたかったのは、**危ないのが「味方」のゲーム**でした。

一緒に脱出するはずの味方AIが、パニックになって誤射する。

勝手に先行してドアを開け、敵を起こす。

しかも「自分の誤射で味方を撃つと即ゲームオーバー」という制約付きです。

つまりプレイヤーは、敵よりも**背後の相棒に神経を使う**ことになります。

ここで一番大事なのは、味方を「ただのバカ」にしないことでした。

理不尽に突然死ぬAIは、ただストレスです。

でも「あ、今の状況ならこいつやらかすな」と**読めるクセ**なら、憎めない相棒になります。

あなたがイライラするゲームAIと、愛せるゲームAIの違いって、どこにあると思いますか?

私の答えは、**「予測できるかどうか」**でした。

### 突然死ではなく「確率」で、読めるクセを作る

![](https://assets.st-note.com/production/uploads/images/294114155/rectangle_large_type_2_33a1fc39177aceae505d6d8888f3218d.png)
読めるクセを作る鍵は、乱数の使い方です。

ダメな設計は、毎フレーム一定確率で「ランダムにやらかす」ことです。

これはプレイヤーから見ると、ただの突然死にしか見えません。

私が採った設計は違います。

**状況を数値化した「メーター」で、やらかしの確率を動かす**のです。

周囲の敵が増えれば、パニックの確率が上がる。

味方の視界から外れると、不安になって挙動が変わる。

つまり「今この状況は危ない」という文脈を、プレイヤーとAIが**同じ数字で共有**します。

だからプレイヤーは、メーターの気配を画面から読み取れる。

「敵に囲まれてきた、そろそろこいつ暴発するぞ」と身構えられるわけです。

**乱数は「有無」ではなく「重み」に使う。** これがこの設計の核心でした。

### 全体アーキテクチャ：FSMの5状態＋2メーター

![](https://assets.st-note.com/production/uploads/images/294114184/rectangle_large_type_2_5de3891d8cea289ed9907ccb3706d639.png)
ここは出し惜しみせず、仕組みを全部説明します。

味方AIは、大きく2つの部品で動いています。

ひとつは**ノードベースのFSM（有限状態機械）**です。

状態は5つ用意しました。

- **Follow**：プレイヤーについていく、平常時の状態

- **Combat**：敵を見つけて交戦する状態

- **Cower**：怯えて縮こまる状態

- **Panic**：パニックで暴発しやすい状態

- **Interact**：ドアを開けるなど、環境に干渉する状態

もうひとつが、**2つの内部メーター**です。

- **緊張度**：自分の周囲にいる敵の数で上下する

- **安心度**：自分が味方（＝プレイヤー）の視界コーンに入っているか

この2メーターが、**各状態への遷移確率と、状態内の行動確率**を動かします。

FSMが「今どの気分か」を決め、メーターが「その気分がどれだけ暴れるか」を決める。

この二層構造が、ポンコツAIの背骨になっています。

### 2つのメーターが、具体的に何を動かすか

![](https://assets.st-note.com/production/uploads/images/294114196/rectangle_large_type_2_133515f30f0f7f7118a1f5eea67a8395.png)
メーターがどう効くか、もう少し具体的に話します。

**緊張度が上がると、CombatやPanicへ遷移しやすくなります。**

敵が1体なら冷静に対処するのに、3体に囲まれると暴発率が跳ね上がる。

これで「囲まれると誤射が怖い」という緊張感が自然に生まれます。

**安心度が下がると、Cowerに落ちやすくなります。**

プレイヤーの視界から外れて置き去りにされると、味方は不安で動けなくなる。

だからプレイヤーは「相棒を視界に入れ続ける」という無言の責任を負います。

面白いのは、この2つが**相反する**場面があることです。

敵から離れれば緊張度は下がるけれど、プレイヤーから離れれば安心度も下がる。

「安全な場所」と「見守られている場所」が一致しないとき、AIは揺れます。

この揺れが、機械なのに感情があるように見える瞬間でした。

数字だけで、どこまで「性格」を作れるか——それがこの設計の挑戦でした。

### やらかしの実装：射線割り込みと勝手なドア

![](https://assets.st-note.com/production/uploads/images/294114241/rectangle_large_type_2_a95e84002b9abf3a096284a725c9a86e.png)
ポンコツさは、抽象的なメーターだけでは伝わりません。

具体的な「やらかし挙動」に落とし込む必要があります。

私が実装した代表的なやらかしは、こうです。

**射線割り込み**：プレイヤーが撃とうとした瞬間、味方が射線に入ってくる。

しかもいきなりではなく、**予兆→回避のチャンス→事故**という段階を踏みます。

「あ、入ってくる」と気づいて撃つのをやめれば助かる。

反応が遅れれば、味方を撃って即ゲームオーバー。

この「予兆」こそが、理不尽と読めるクセの分かれ目でした。

**勝手なドア開け**：Interact状態の味方が、先走ってドアを開ける。

その奥で寝ていた敵が起きて、静かに進みたかった計画が崩れる。

どちらも「AIが自分の判断で動いた結果」に見えるのがポイントです。

プレイヤーが「余計なことを…」と苦笑する。

その苦笑が出た時点で、このAIは「相棒」になっていました。

### 地雷リスト：先に一覧で渡します
コードの前に、私が実際に溶かした罠を先に一覧化します。

自分でやると、この一つ一つで数十分〜数時間が消えます。

### 設計判断：FSMとメーターを、なぜ分けたか
まず、いちばん大事な設計判断の理由です。

「FSM」と「メーター」を、なぜ2つの別部品に分けたのか。

一体化させて「状態ごとに確率を直書き」する手もありました。

でもそれをやると、**状況（文脈）と気分（状態）が混ざって**、調整不能になります。

分けた理由はこうです。

- **FSM＝離散的な「今どの気分か」**（Follow/Combat/Cower/Panic/Interact）

- **メーター＝連続的な「その気分がどれだけ暴れるか」**（緊張度・安心度）

FSMは「状態」なので、遷移は飛び飛びです。

メーターは「量」なので、なめらかに上下します。

この2つを掛け合わせることで、**「同じPanic状態でも、緊張度で暴発率が変わる」**が表現できます。

もし一体化していたら、Panicの中に「弱いPanic」「強いPanic」と状態を増やす羽目になります。

状態爆発を避けるために、**連続量はメーターに逃がす**。これが分離の狙いでした。

**メーターが確率を動かす、実装の骨格**

メーターがどう確率に効くか、骨格を示します。

考え方は「メーターを0〜1に正規化して、遷移確率の重みに掛ける」だけです。

```
# 周囲の敵数から緊張度を、視界内フラグから安心度を更新する
func update_meters(comp: CompanionUnit, raid: RaidState) -> void:
    # 近くの敵をカウント（型付き配列で受ける）
    var nearby: Array[EnemyUnit] = raid.enemies_within(comp.position, DANGER_RADIUS)
    # 緊張度：敵が多いほど上がる（上限で頭打ち）
    comp.tension = clampf(float(nearby.size()) / MAX_TENSION_ENEMIES, 0.0, 1.0)
    # 安心度：プレイヤーの視界コーンに入っていれば上がる
    comp.safety = 1.0 if raid.player_sees(comp) else comp.safety - SAFETY_DECAY

# パニックへ遷移する確率を、緊張度で重み付けする
func panic_chance(comp: CompanionUnit) -> float:
    # 基礎確率に緊張度を掛け、下限・上限でクランプ
    return clampf(BASE_PANIC * comp.tension, PANIC_MIN, PANIC_MAX)
```
ポイントはclampfでの**下限・上限のクランプ**です。

下限を0にすると「絶対やらかさない」瞬間ができて、緊張感が消えます。

上限を外すと「必ずやらかす」理不尽になります。

**やらかしの確率は、0でも1でもない帯に閉じ込める。** ここが調整の勘所でした。

### 確率テーブルの調整指針：理不尽と愛嬌の境目
数値をどう詰めたか、指針を共有します。

私が回した調整は、この3つの軸でした。

**1軸め：予兆の長さ。**

やらかしが確定してから、実際に事故るまでの猶予フレーム数です。

短すぎると「反応できない理不尽」、長すぎると「余裕で回避できて緊張感ゼロ」。

プレイヤーが「気づけば避けられる」ギリギリを狙います。

**2軸め：メーターの立ち上がりの速さ。**

敵が増えたとき、緊張度がどれだけ急に上がるか。

急すぎると突然死、緩すぎると危機感が伝わらない。

**3軸め：確率の下限・上限の幅。**

前述のクランプの帯を、どれだけ広く取るか。

狭いと単調、広いと博打になります。

この3軸を回して探したのは、**「やられた瞬間に、プレイヤーが自分のミスだと納得する」**点でした。

「AIが悪い」ではなく「見てなかった自分が悪い」と思える。

そこに着地したとき、ポンコツAIは相棒になります。

あなたなら、予兆の猶予を「長め」と「短め」、どちらから詰めますか?

私は短めから始めて、理不尽だと感じるたびに伸ばしていきました。

### Variant地雷の全貌：:=が連鎖で死ぬ理由
ここからGDScriptの地雷です。まずVariant問題。

症状は、**:=（型推論代入）がパースエラーを大量に吐く**というものでした。

一見、代入の書き方が悪いように見えます。

でも真犯人は、その手前の**未型の参照**でした。

たとえば、こう書いたとします。

```
# NG：compを型無しで受けると…
var comp = get_companion()      # 型が推論されずVariant扱い
var raid = get_raid()           # これもVariant

# するとメンバアクセスの戻りが全部Variantになり…
var enemies := raid.enemies_all()   # ← :=がVariantを推論できずパースエラー
```
compやraidを型無しで受けると、それらのメンバアクセスの戻りが**全部Variant**になります。

Variantは「何の型か確定できない」ので、:=は型を推論できません。

結果、**一箇所の未型が、下流の:=を軒並みパースエラーにする**連鎖が起きます。

だからエラーの数を見て焦っても、直すべきは1箇所——**源流の型付け**だけです。

```
# OK：参照を型付けすると、下流の:=が全部生き返る
var comp: CompanionUnit = get_companion()
var raid: RaidState = get_raid()
var enemies: Array[EnemyUnit] = raid.enemies_all()  # 型が通り := も使える
```
comp／raidをclass_nameで型付けし、配列はArray[EnemyUnit]で型付けする。

これだけで、連鎖していたパースエラーが一斉に消えました。

**「エラーの数」ではなく「Variantの源流」を探す。** これがVariant地雷の唯一の攻め方でした。

### 真っ白画面の直し方：Controlの自動リサイズ
2つめの地雷、画面が真っ白になる問題です。

症状は、**コードは正しいのに、起動すると何も映らない**というもの。

原因は、Controlノードの置き方にありました。

Controlは、親のサイズに合わせて自動リサイズされる前提の子です。

ところが**Nodeの直下に素で置くと、その自動リサイズが効きません**。

サイズが0のまま、あるいは想定と違うサイズになり、中身が画面外に飛ぶ。

結果、画面が真っ白になります。

解決は、**論理解像度（基準解像度）を明示する**ことでした。

project.godot側でウィンドウの基準サイズとストレッチ設定を明示し、UIの土台となるControlのアンカーを画面いっぱいに設定する。

こうすると、Controlが正しく画面サイズに追従して、中身が映るようになります。

「真っ白＝描画が壊れた」と思い込むと、レンダリング周りを延々疑って溶かします。

でも真犯人は**レイアウト（サイズが0）**でした。

**真っ白を見たら、まずノードのサイズを疑う。** これは覚えておいて損はありません。

### マップ生成②方式：連結性をBFSで検証する
やらかしAIが活きるには、ステージが成立している必要があります。

でも自動生成したマップは、**部屋が分断されてクリア不能**になることがあります。

そこで採ったのが、**生成②方式（連結性検証＋シード）**です。

やることは2つ。

**1つめ：シードで再現可能にする。**

同じシードなら同じマップが出る。バグ再現とテストが一気に楽になります。

**2つめ：生成後にBFSで連結性を検証する。**

スタートからゴールまで、実際に到達できるかを幅優先探索で確認します。

到達できなければ、そのマップは**捨てて、シードを変えて再生成**する。

```
# スタートからゴールへ到達可能かをBFSで検証する
func is_connected(grid: MapGrid, start: Vector2i, goal: Vector2i) -> bool:
    var queue: Array[Vector2i] = [start]
    var seen := {start: true}
    while not queue.is_empty():
        var cur: Vector2i = queue.pop_front()
        if cur == goal:
            return true
        for nb in grid.walkable_neighbors(cur):
            if not seen.has(nb):
                seen[nb] = true
                queue.append(nb)
    return false   # ここに来たら分断されている＝採用しない
```
「生成して祈る」のではなく、「生成して検証して、ダメなら捨てる」。

**クリア不能マップは、リリース後に踏まれたら致命傷**です。

だからこそ、生成の段階で必ず連結性を保証する。これが②方式の狙いでした。

### 循環class_name参照は、避けなくてよかった
最後に、地雷だと身構えたのに問題なかった話です。

GDScriptでclass_name同士が互いを参照する「循環参照」。

古い情報では「循環参照は避けろ」とされがちです。

私も最初、CompanionUnitとRaidStateが相互参照する構成を怖がっていました。

でも結論、**Godot 4.6では循環class_name参照は問題なく動きました**。

型付けのために相互参照が必要でも、避けて設計を歪める必要はなかった。

「地雷だと思っていたものが、実は地雷じゃなかった」。

これも、実際に踏みに行って初めて分かることでした。

**古い『避けろ』情報を鵜呑みにせず、今のバージョンで一度試す。** これも一つの手です。

### カスタマイズの勘所：3点だけ
自分のゲームに応用する際、押さえるのはこの3点です。

**1点め：メーターは「相反する2つ」にする。**

緊張度と安心度のように、**片方を満たすともう片方が犠牲になる**組み合わせにする。

すると、AIが「揺れる」瞬間が生まれ、性格が立ちます。

**2点め：やらかしには必ず予兆を付ける。**

予兆→回避猶予→事故の3段階を守る。

予兆のない乱数は、ただの理不尽です。

**3点め：確率は0と1に振り切らせない。**

clampfで下限・上限の帯に閉じ込める。

「絶対やる／絶対やらない」が消えた瞬間、AIは生き物っぽくなります。

この3点だけ守れば、あなたのゲームのAIも「読めるポンコツ」になります。

### まとめと次回予告
ポンコツ味方AIの実装で学んだことは、一言で言えばこうです。

**やらかしは乱数の「有無」ではなく、メーターで動かす「確率の重み」で作る。**

そして、**FSMで気分を、メーターでその暴れ方を分けて持つ**と、状態爆発せずに性格が出せる。

GDScriptでは、**未型参照がVariant連鎖でビルドを全滅させる**点と、**Controlの素置きで画面が真っ白になる**点だけ、先に知っておけば時間を溶かさずに済みます。
