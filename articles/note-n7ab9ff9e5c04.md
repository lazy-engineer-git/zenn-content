📌 **この記事は「AIを使い始めたけど、毎回同じ説明をするのが面倒になっているエンジニア」向けです。**
Claude Codeに仮想の組織を持たせることで、一人開発がチーム開発のように変わった話を書きます。

### AIを使い始めて最初にぶつかった壁
私がClaude Codeを本格的に使い始めたのは、副業で月10万円を稼ごうと決めた頃のことです。

当時、AIの活用方法はほとんどわかっていませんでした。
「とりあえずプロンプトを打てば何かしてくれる」くらいの認識で使い始めました。

ところが、すぐに大きなストレスに直面しました。

仕事の文脈を毎回最初から説明しなければならないのです。

「今作っているのはChrome拡張で、フリーミアム構成で、Gumroadでライセンス認証をしていて…」
セッションを開くたびに同じことを打ち込んでいました。
しかもClaude Codeはセッションをまたぐとメモリが消えます。
昨日決めたことが今日には消えている。
同じ議論を何度もやり直す羽目になる。

「AIは便利と聞いていたのに、なんで自分はこんなに手間がかかっているんだろう」と正直感じていました。

副業の作業時間は限られています。
仕事終わりの2〜3時間、休日の数時間しか使えません。
その貴重な時間の一部が「コンテキスト設定」に溶けていく感覚は、思っていた以上にストレスでした。

もう一つ、気になっていたことがありました。

Claudeは賢いのですが、毎回「まっさらな新入社員」として接してきます。
「先週話したあの件ですが」が通じない。
「前回と同じようにやって」も通じない。

人間のチームでこれをやったら仕事になりません。
でもAIとの作業ではこれが普通のことになっています。
これは構造的な問題で、何とかしないといけないと思い始めました。

気づけば毎セッション最初の10分が「説明タイム」になっていました。
作業時間の10〜20%がゼロ地点に戻るコストとして消えていく状態です。
「これが続くと副業どころではない」と感じました。

### 「仮想組織」というアイデアに辿り着くまで
この問題を解決したくていろいろ調べていると、Claude Codeに `CLAUDE.md` というファイルを置くと、起動時に自動で読み込んでくれることを知りました。

最初は「プロジェクトのメモ置き場」として使い始めました。
「このプロジェクトはChrome拡張だ」「認証はGumroadを使っている」という事実を書いておくだけでも、毎回の説明が不要になりました。

これだけでかなりストレスが減りました。
「知っている状態」でセッションが始まるというのは、当たり前のようで革命的でした。

でも使っていくうちに、もっと面白い使い方に気づきました。

人間が仕事をするとき、「この人はどんな役割で、何を大事にしているか」というキャラクターがありますよね。
エンジニアなら技術的な正確さを重視するし、秘書なら段取りとメモを重視する。
Claudeにもそのキャラクターを持たせることができるのではないか、と考えました。

そこから「仮想組織」というアイデアが生まれました。

部署ごとに役割を定義して、ClaudeがそのCLAUDE.mdを読むことで「今自分はどの役割で動いているか」を意識して動く。
プロジェクト全体で管理できたら、一人でも"チームで開発している感覚"で進められるのではないか。

最初は半信半疑でした。
でも「どうせファイルを読み込んでいるだけだし、失敗してもコストはほぼゼロだ」という気持ちで試してみました。

構想から実装まで、約8時間かかりました。

8時間というと長く聞こえますが、部署の設計に悩んだ時間と、実際に動かして修正した時間が大半です。
「ファイルを作る」だけなら1時間以内で終わります。
でも「どう書いたらClaudeが意図通りに動くか」の試行錯誤が一番時間がかかりました。

### 実際に何を作ったか
`.company/` というディレクトリを作り、その中に仮想組織を構築しました。

```
.company/
├── CLAUDE.md ← 組織全体のルール
├── secretary/ ← 秘書室（窓口・記録・TODO）
├── manager/ ← マネージャー（進捗・収益管理）
├── engineering/ ← 開発（技術設計・デバッグログ）
├── research/ ← リサーチ（市場調査・競合分析）
└── content/ ← コンテンツ（note記事・執筆・投稿管理）
```

仕組みはシンプルです。

Claude Codeがプロジェクトを開くと、プロジェクトルートの `CLAUDE.md` を自動で読み込みます。
そのCLAUDE.mdに「セッション開始時に必ず `.company/CLAUDE.md` を読み込め」と書いておきます。
すると、組織全体のルールが常に適用された状態でClaudeが動き始めます。

各部署のCLAUDE.mdは、その部署のフォルダに置いてあります。
秘書が動くときは秘書のCLAUDE.mdが参照され、開発作業のときは開発のCLAUDE.mdが参照されます。

「ファイルを読んでいるだけ」の仕組みです。
でも、これが驚くほどうまく機能しました。

重要なのは、このすべてがローカルファイルで完結していることです。
APIの課金は会話ごとに発生しますが、CLAUDE.mdはファイルなので追加費用がかかりません。
「設定ファイルに書いておくだけで挙動が変わる」という仕組みがうまく活きています。

### 5つの部署とそれぞれの役割
### 秘書室

組織の窓口です。私との対話はすべて秘書が受け取ります。

秘書の仕事は主に3つです。

- **TODO管理** — 日次ファイルを自動作成・更新（`todos/YYYY-MM-DD.md`）

- **意思決定の記録** — `notes/YYYY-MM-DD-decisions.md` に自動追記

- **作業を部署に振り分ける** — 技術的な作業なら開発部署のフォルダへ書き込む

特に自動記録が強力です。
私が何かを決めると確認なしでファイルに書き込んでくれます。
「〜にする」「〜でいく」と言うだけで、意思決定ログが残ります。

### マネージャー

プロジェクトの進捗管理と収益目標のトラッキングを担当します。
「月10万円目標に対して今どこにいるか」を常に把握しておく役割です。

稼働中のプロジェクトは現在3つです。
Chrome拡張（CWS審査中）、在庫監視サービス（APIキー取得待ち）、noteの自動投稿パイプライン（稼働中）。
それぞれの状態と次のアクションをマネージャーが把握しています。

「プロジェクトXの今の状態は？」と聞けば、マネージャーが整理して答えてくれます。

### 開発

技術ドキュメント・設計書・デバッグログを管理します。
バグを直したとき、原因と対処法を自動でログに残してくれます。
同じバグを二度踏まないための知識ベースです。

最近はnoteの非公式APIの仕様（どのエンドポイントが使えてどれが使えないか）も開発部署のメモに自動で蓄積されています。
これが翌セッションでも参照できるので、「前回どうやって解決したっけ？」がなくなりました。

たとえば「noteのPUT APIがある日から422エラーを返すようになった」という問題が起きたとき。
原因と対処法を特定してデバッグログに書いておくと、翌週同じ問題に直面したときに「以前解決したバグと同じですね」と参照してくれます。

### リサーチ

市場調査・競合分析・次に作るものの検討を担当します。
「これを作ったら売れるか？」という壁打ちの相手です。

SNSをやっていないので、リサーチの対象はGumroadのレビューやnoteのコメント、競合ツールのフィードバックが中心です。
「次に何を作るか」の判断材料をまとめる役割です。

### コンテンツ

note記事の企画・執筆・投稿・シリーズ管理を担当します。
タイトルフォーマット、画像スタイル、有料記事の価格基準など、記事に関するルールもここで一元管理しています。
SNSはやっていないので、noteとGumroadに集中した役割設計にしています。

このブログのシリーズ進捗もコンテンツ部署のCLAUDE.mdに書いてあります。
「今何本目まで書いたか」「次は何を書くか」がいつでも参照できます。

### 秘書が想像以上に優秀だった
5つの部署を作ってみて、最も活躍しているのは秘書室です。

何が優秀かというと、**「確認なしで動く」** ことです。

普通のClaude Codeとの会話では、何かを記録しようとすると「〇〇を記録しますか？」と聞いてきます。
毎回「はい」と答えるのも地味に面倒です。

秘書のCLAUDE.mdに「意思決定が発生したら確認不要で即記録せよ」と書いてあるので、私が「〜にする」と言った瞬間にファイルへの書き込みが走ります。

この記事のタイトルフォーマットを変更すると決めた瞬間も、秘書が意思決定ログに追記しました。
私は何も指示していません。ただ「この形式にしよう」と言っただけです。

この「能動的に記録してくれる」感覚が、思った以上に働くモチベーションに繋がっています。

さらに、翌日作業を再開したときの体験が変わりました。
以前は「昨日どこまでやったっけ？」と確認する時間が毎回必要でした。
今は「今日の作業状況を教えて」と聞くだけで、前回のTODOや意思決定ログをもとに整理してくれます。

人間のチームでいえば「昨日の議事録をまとめておきました」と言ってくれる優秀な秘書です。

あなたは作業メモをどこに残していますか？
「頭の中に入れたまま翌日に持ち越している」なら、この仕組みは特に刺さると思います。

### 工程を教えたら、ほぼ全自動になった
この仮想組織を作って、一番驚いたことがあります。

**「作業の工程・順番を定義すると、ほぼ全自動で動く」**ことです。

たとえばnote記事の投稿フローを考えてみます。
記事のMarkdownを書く → note用HTMLに変換 → APIで下書き保存 → 公開。
この手順をCLAUDE.mdやスキルファイルに定義しておくと、「記事を投稿して」の一言でClaudeが順番通りに動きます。

最初は「AIってそんなに自律的に動けるの？」と半信半疑でした。
でも実際にやってみると、かなりの精度で順番通りに処理してくれます。

具体的には、コンテンツ部署のCLAUDE.mdにこう書いてあります。

```
## 投稿手順
1. articles/ 以下の指定Markdownファイルを確認する
2. post_draft.py --file <ファイル名> を実行して下書き保存する
3. 返ってきたURLを報告する
```

これだけです。
「記事を投稿して」の一言で3ステップが自動で走ります。

今まで「AIはアシスタント」という意識がありましたが、工程を教えることで「AIは実行者」に変わりました。
私はゴールを指示するだけでよくなったのです。

この感覚の変化が、一番の収穫だったかもしれません。

工程を定義することのもう一つのメリットは、「自分の仕事のやり方が言語化される」ことです。
普段なんとなくやっていた作業を文章にする過程で、「これって本当に必要なステップだっけ？」と見直すきっかけになります。

### うまくいかなかったこと、見直しの繰り返し
正直に書くと、最初からうまくいっていたわけではありません。

Claudeが意図を正しく読み取れていないと感じることが、何度かありました。

**失敗①：自動記録が走りすぎた**

最初のCLAUDE.mdが曖昧な書き方だったので、ちょっとした会話でもどんどんファイルに書き込んでしまいました。
「〇〇かもしれない」という仮の話も記録してしまう。
打ち合わせの雑談も意思決定として残してしまう。

「それは記録しなくていい」という判断基準が定義されていなかったのです。

そのたびにCLAUDE.mdを見直して、「〇〇のときだけ記録する」「〇〇は記録不要」という条件を明確にしました。
今は「〜にする」「〜を採用する」という確定の言葉があったときだけ記録するよう定義しています。

**失敗②：口調が自分と合わなかった**

最初の秘書は「いいですね！」「承知しました！」と元気よく返してくれたのですが、作業中にそれが続くと逆にテンポが崩れる感じがしました。
応援されたいわけではなく、静かに仕事をしてほしい。

「結論を先に言う」「短く返す」「絵文字は最小限」という行動ルールを追加したことで、自分のペースで作業できるようになりました。

**失敗③：部署名が他の人の設定と被った**

`.company/` の中に `pm/`（PM部署）と `marketing/`（マーケ部署）を作っていたのですが、他の人も同じ名前で作っているケースが多いと気づきました。
競合を避けるためにそれぞれ `manager/`、`research/` にリネームしました。

部署名はプロジェクトに合わせてユニークなものにした方が、混乱が少ないです。

CLAUDE.mdの改善は「AIに仕事を教えていく作業」に近い感覚です。
新入社員を教育するとき、最初は細かく指示して、徐々に任せる範囲を広げていく。
それと同じことをCLAUDE.mdで実現しています。

今でも「あ、これはCLAUDE.mdの書き方が曖昧だったな」と気づくことがあります。
見直しは今も続いています。
一度定義してしまえばずっと使えるので、設定コストは最初に払うだけです。

### 8時間かけて作った今、どう使っているか
この仮想組織を作ってから、毎日の開発作業が変わりました。

このブログ記事の執筆もそうです。
「#3を投稿したいので、内容を教えて」と聞くだけで、秘書がこれまでの決定事項を確認して「#3はこういう内容でしたね」と答えてくれます。
私は記憶をたどる必要がありません。

Chrome拡張の開発でバグが出たとき、解決したら自動でデバッグログが残ります。
翌週同じようなバグが出たとき、「以前似た問題がありましたね」と参照してくれます。

note記事の下書きをAPIで保存するフローも、「投稿して」の一言で動きます。
記事を書いて・変換して・保存する3ステップが1アクションになりました。

一人開発をしていると、どうしても「自分の頭の中にしかない文脈」で作業が進みがちです。
仮想組織はその文脈をファイルに外部化してくれます。

「第二の脳」という言葉がありますが、私にとってはそれに近い感覚です。
しかも脳と違って、翌朝になっても忘れません。

累計で考えると、毎セッション10分のコンテキスト設定がゼロになったとして、1日1セッションなら月300分（5時間）の節約です。
その時間を開発や記事執筆に使える。
これが一番の価値だと感じています。

### CLAUDE.mdの書き方：なぜそう書くか
CLAUDE.mdはただのメモファイルではありません。
Claudeへの「行動指示書」です。
何を書くかより、**どう書くか**が効果を左右します。

以下では、私が実際に使って効果があった書き方のポイントをまとめます。

### ポイント①「やってはいけないこと」を先に書く

最初に私が失敗したのは、やってほしいことしか書かなかったことです。

秘書のCLAUDE.mdに「意思決定を記録する」とだけ書くと、Claudeはすべてを記録しようとします。
雑談も、仮の話も、全部ファイルに書き込んでしまいました。

禁止事項を明示することで、Claudeの判断基準が生まれます。

```
## やってはいけないこと
- 「念のため確認させてください」を連発しない
- 「やっておきました」と言いながら実際にはやっていない
- 実行結果なしの報告
```

「やること」より「やらないこと」を書く方が、意図した動きに近づきます。
これは普通の仕事のマニュアル作りと同じですが、AIへの指示では特に効果が大きいです。

### ポイント②トリガーと記録先をセットで書く

「意思決定を記録する」という指示は曖昧です。
「いつ・どこに・何を」まで書くことで、確認なしで動けるようになります。

```
## 自動記録（確認不要・即実行）
- 「〜にする」「〜を採用する」と確定したとき
→ secretary/notes/YYYY-MM-DD-decisions.md に追記
- バグの原因と対処法が確定したとき
→ engineering/debug-log/YYYY-MM-DD-issue.md に記録
- 新しい知見・APIの挙動が判明したとき
→ secretary/notes/YYYY-MM-DD-learnings.md に追記
```

トリガーの例文を具体的に書くほど、Claudeの判断精度が上がります。
「〜にする」という言葉が入ったら記録する、という基準が明確になるからです。

また、「確認不要・即実行」と明記することが大事です。
これがないと「記録しますか？」と毎回聞いてきます。

### ポイント③部署ごとに「役割外のこと」を定義する

各部署は役割が明確なほど動きがよくなります。
特に「うちの部署はこれをやらない」を書くのが重要です。

たとえばリサーチ部署のCLAUDE.mdには、こう書いてあります。

```
## 役割
次に作るものを考えるための調査・分析を担当する。
note記事の管理は content/ が担当する。
```

「note記事の管理はここではやらない」と明示することで、記事に関する質問が来たとき、リサーチ部署は答えを出さずにコンテンツ部署に振ります。

役割外の仕事を受け付けないことで、各部署の専門性が保たれます。

### ポイント④オーナーの好みを組織ルールに書く

組織全体のCLAUDE.mdに、自分の好みを書いておくことが重要です。

```
## オーナーの好み（必ず守る）
- 結論を先に言う。説明は後
- 確認を連発しない。明らかに必要なときだけ確認する
- 短く簡潔に
- 絵文字は最小限（📌🎯💡✅のみ）
```

このルールがあることで、すべての部署がこの基準で動くようになります。
秘書だけ設定して開発部署に設定し忘れる、という事態を防げます。

私の場合、最初は絵文字も使い放題にしていました。
するとClaudeが毎返信で大量の絵文字を使うようになって読みにくかったです。
「この絵文字だけOK」と限定することで解決しました。

### ポイント⑤日付を常に確認させる

CLAUDE.mdに「ファイル操作の前に必ず今日の日付を確認する」と書いておくことが重要です。

理由は単純で、Claudeは日付を正確に把握していないことがあるからです。
特にファイル名に日付を使う場合（`2026-06-08-decisions.md` など）、間違った日付でファイルが作られると混乱します。

```
## 日付チェック
- ファイル操作の前に必ず今日の日付を確認する
- 確認後に YYYY-MM-DD 形式でファイル名に使う
```

実際にこのルールを入れてから、日付の間違いはほぼゼロになりました。

### ポイント⑥同日ファイルへの追記ルールを明示する

自動記録が走るとき、毎回新しいファイルを作られても困ります。
同じ日に複数の意思決定があれば、同じファイルに追記してほしい。

```
## 同日1ファイルルール
- 同じ日付のファイルが存在する場合は追記する
- 新規作成しない
```

このルールがないと、`2026-06-08-decisions-1.md`、`2026-06-08-decisions-2.md` のようにファイルが増殖します。
一見小さなルールですが、あとでファイルを見返すときの快適さが全然違います。
