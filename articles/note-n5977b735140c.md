### 月曜の朝、Zennに記事が「生えてくる」ようになった

![](https://assets.st-note.com/production/uploads/images/284865985/rectangle_large_type_2_8ea39d37bb6be298982bee2c9b8e85c6.png)
まず、できあがったものから見せます。

来週の月曜朝、私が寝ている間に、Zennへ週刊まとめ記事が自動公開されます。
中身はもう確認済みです。
「AIスコアで選ぶ 今週のGitHub注目リポジトリ 9選」という記事が、すでに手元で生成されています。

1位はスコア78点のセルフインタビューツール。
ランキング表、各リポジトリの解説、評価コメントまで全部入りです。
そして、この記事を私は**1文字も書いていません**。

今回の設定にかかった手作業は、**実質15分・4ステップ**でした。

この記事は、こんな人に向けて書いています。

- noteで書いているけど、**Zennにも出すべきか迷っている**人

- 自動投稿を運用していて、**新規の読者の入口を増やしたい**人

- 「同じ記事を2か所に貼るのはなんか違う」と感じている人

読み終わると、noteの投稿パイプラインにZennクロス投稿を足す手順と、**「どの頻度で流すか」という設計の考え方**がわかります。

### きっかけ：閲覧20件の壁

![](https://assets.st-note.com/production/uploads/images/284866040/rectangle_large_type_2_92482c7f7da1da800a8ee5f69f92514f.png)
**記事は毎日増える。読者は増えない**

私はnoteで、AIによる記事の自動投稿を運用しています。
毎朝7時ごろ、GitHubのAI系注目リポジトリをまとめた記事が自動で公開されます。

このnote自体も、実録シリーズとして#1から#7まで書いてきました。
スタート宣言から数えて、運用はまだ2週間足らずです。
記事のストックは自動投稿のおかげで毎日増えていきます。

仕組みは順調に動いています。
でも、肝心の数字が動きません。

**1記事あたりの閲覧は20件前後。スキは1つ付けばいいほう**です。

中身の問題もあるとは思います。
ただそれ以上に、「そもそも入口が足りない」と感じていました。
noteの中だけで新しい読者と出会うのは、フォロワーが少ないうちは厳しい戦いです。

あなたなら、入口を増やしたいとき、まずどこに出しますか？

**Xはやらない。じゃあどこへ？**

定番の答えは「Xで宣伝する」だと思います。
実は自動ポストの実装まで作りました。

でも、**見送りました**。

- 私はSNSを運用しない方針（消耗するのが目に見えている）

- フォロワー0からの自動ポストは、流入効果がほぼ無い

- API代は月45円程度でも、アカウント管理のコストが残る

「楽するために自動化する」のが私のスタンスです。
管理対象が増えて気が重くなるなら、それは楽になっていません。

そこで目を付けたのがZennでした。
Zennは「SNS」ではなく「書く場所」です。
エンジニア読者が濃く、私の記事との相性も良いはず。
方針に反しない入口は、ここしかありませんでした。

### Zennの「GitHubからのデプロイ」が自動化向きすぎる

![](https://assets.st-note.com/production/uploads/images/284866092/rectangle_large_type_2_8d2ebaa8e14c5ccd4ba3bd445437f4a8.png)
**pushしたら公開される。それだけ**

Zennには「GitHubからのデプロイ」という公式機能があります。
連携したリポジトリにMarkdownをpushすると、それだけで記事が公開されます。

APIキーも、Cookieも、ヘッドレスブラウザも要りません。
**gitでpushできるなら、それがそのまま投稿手段になる**んです。

noteの自動投稿を作ったときは、非公式APIの調査にかなり苦労しました。
Cookieの期限に怯え、エンドポイントの仕様変更に振り回されました。
その話は[実録#4](https://note.com/lazy_engineer/n/n47e75db1463f)に書いています。

それと比べると、Zennは拍子抜けするほど簡単でした。
公式がこの仕組みを用意してくれているのは、本当にありがたいです。

**記事ファイルの形式もシンプル**

Zennの記事は、frontmatter付きのMarkdownファイル1枚です。

```
---
title: "AIスコアで選ぶ 今週のGitHub注目リポジトリ 9選"
emoji: "📡"
type: "tech"
topics: ["ai", "github", "llm", "生成ai"]
published: true
---
```
published: true で置けば、pushと同時に公開されます。
つまりやることは、**「記事のMarkdownを生成して、リポジトリにpushする」だけ**。

毎朝のnote投稿はすでにGitHub Actionsで動いています。
この仕組みの全体像は[実録#5](https://note.com/lazy_engineer/n/n1a0f9c3669d7)で公開しました。
そのActionsに「Zenn用のMarkdownを書いてpushする」ステップを足せば完成です。

**集計は「日次の結果」に依存させない**

実装で1つだけ、こだわった設計判断があります。

週刊記事の元データを、**毎日の投稿結果ファイルからではなく、データベースから直接集計する**ことにしました。

毎日の自動投稿は、収集したリポジトリ情報をスコア付きでデータベースに貯めています。
週刊記事はそこから「直近7日間のスコア上位」を引き直すだけです。

なぜこうしたかというと、日次の処理は普通に失敗するからです。
実際、この1週間だけでもアイキャッチの設定漏れが1回ありました。
日次の結果ファイルに依存すると、**どこか1日コケただけで週刊記事まで巻き添え**になります。

データベースから引き直す方式なら、途中の1日が欠けても週次は成立します。
自動化は「失敗する前提」で組むほど、運用が楽になります。

あなたの自動化は、どこか1か所コケたら全部止まる作りになっていませんか？

**リライトが失敗したときの保険も入れる**

リード文はClaude Haikuで毎回リライトすると書きました。
ここにも保険があります。

- APIキーが無い、またはAPI呼び出しが失敗 → **定型文3パターンの日替わり**に自動フォールバック

- リライト結果が短すぎる・長すぎる（20字未満や300字超） → 採用せず定型文へ

AIに任せる処理は、出力が安定しない前提で受け皿を作っておきます。
「AIが変な文を返したら記事ごと壊れる」では、安心して寝られません。

### 一番悩んだのは、技術ではなく「頻度」

![](https://assets.st-note.com/production/uploads/images/284866105/rectangle_large_type_2_892b7b36bb60833f835c4480fd449284.png)
**毎日流すほうが、実装はずっと簡単**

ここで1つ、立ち止まりました。

実装だけ考えれば、毎日のnote記事をそのままZennに流すのが一番簡単です。
できあがった記事データを、形式だけ変えてpushすればいい。

でも、それをやったらどうなるか。

**毎朝、AI生成のランキング記事が自動でZennに並び続ける**わけです。

Zennを読んでいる方ならわかると思います。
あそこはエンジニアが手で書いた記事の文化が強い場所です。
そこにAI生成記事が毎日機械的に流れてきたら、どう見えるでしょうか？

たぶん、スパム扱いです。
読者の信頼を失ったら、入口を増やすどころか逆効果になります。

**「自動化できる」と「やっていい」は別の話**

なので、**週1回に絞りました**。

毎週月曜の朝、直近7日間のスコア上位をまとめた「週刊記事」だけを流します。
毎日の記事はnoteで、まとめはZennで。
プラットフォームごとに、受け入れられる温度感は違います。

自動化を作っていると、つい「流せるだけ流したく」なります。
でも頻度の設計こそが、自動投稿でいちばん大事な意思決定だと思っています。

**重複コンテンツにしない3つの工夫**

「同じ内容の使い回し」にならないよう、3つの対策を入れました。

1. **冒頭のリード文を、毎回AIでリライトする**（Claude Haikuで書き換え）
2. **記事の構成自体をnoteと変える**（Zenn版は週次集計のランキング表形式）
3. **noteへの誘導は記事末尾の1ブロックだけ**（宣伝色を抑える）

クロス投稿はやり方を間違えると、検索評価でも両方の媒体で損をします。
「別の読者に向けて、別の形で出し直す」のが基本方針です。

**そもそも、noteとZennをどう使い分けるか**

ここで私なりの整理を書いておきます。
「noteとZenn、どっちに書けばいいのか」は、よく見る悩みだからです。

私の答えは、**役割を分けて両方使う**です。

- **note = 母艦**。実録シリーズの連載と、有料記事・マガジンによる収益化はこちら

- **Zenn = 入口**。エンジニア読者との接点を作り、noteへ流す

noteは有料記事の仕組みが強く、月10万円という私の目標に直結します。
一方で、エンジニアが技術情報を探しに来る場所としてはZennのほうが濃い。

だから「どっちか」ではなく、**Zennで出会って、noteで読み続けてもらう**形にしました。
入口と母艦を分けると、それぞれの媒体で無理をしなくて済みます。

あなたがいま書いている場所は、入口ですか？それとも母艦ですか？

### やったこと：手作業は実質4ステップ

![](https://assets.st-note.com/production/uploads/images/284866145/rectangle_large_type_2_38522a6d03c648a3fabeee6e4f6fc9dc.png)
ここからは実際の設定作業です。
コードの改修はAI（Claude Code）に任せたので、私の手作業は4つだけでした。

**ステップ1：Zenn連携用のリポジトリを作る（0分）**

GitHubに zenn-content という公開リポジトリを作ります。
中身は articles/ フォルダが1つあるだけでOKです。

これはAIに「作って」と頼んだら、gh CLIで一瞬で終わりました。
私の作業時間はゼロです。

やっていることは、これだけです。

```
gh repo create zenn-content --public --source  --push
```
「リポジトリを作る」というと身構えますが、実体は空フォルダ1つのpushです。
Zenn公式のCLI（zenn-cli）を入れる方法もありますが、自動生成で記事を置くだけなら必須ではありません。

**ステップ2：Zennにアカウント登録して連携（5分）**

Zennの登録はGitHubアカウントでログインするだけです。
登録後、ダッシュボードの「GitHubからのデプロイ」から先ほどのリポジトリを連携します。

画面に「1つのリポジトリと連携中」と出たら完了です。
対象ブランチ（main）に更新があると、自動でデプロイされるようになります。

**ステップ3：Fine-grained PATを発行する（10分）**

GitHub Actionsから zenn-content リポジトリにpushするには、トークンが必要です。
ここは後述しますが、**今回いちばん迷った場所**でした。

ポイントは権限を最小にすることです。

- 対象リポジトリ: zenn-content の**1つだけ**

- 権限: **Contents の Read and write のみ**

- 期限: 1年

これだけで、Actionsからのpushには十分です。

**ステップ4：Secretsに登録する（0分）**

発行したPATを、Actionsが動くリポジトリのSecretsに登録します。
これもAIに渡して代行してもらいました。

登録するSecretは2つだけです。

- ZENN_REPO … 連携リポジトリ名（ユーザー名/zenn-content）

- ZENN_PAT … さっき発行したトークン

gh CLIなら gh secret set コマンド一発で入ります。
ブラウザでSettings画面を開く必要すらありません。

登録後、そのPATで実際にリポジトリへアクセスできるか疎通テストまで実施。
GitHubのAPIにそのトークンで問い合わせて、**push権限: True** が返ってきて設定完了です。

ここまでやって、トークンの値はもう手元に残していません。
Secretsに入れたら原本は捨てる。これも漏洩対策の基本です。

期限の1年後に再発行が必要なことだけ、TODOとして記録してあります。
未来の自分への申し送りは、覚えておくのではなく書いておく主義です。

### AIに任せたこと、自分でやったこと

![](https://assets.st-note.com/production/uploads/images/284866199/rectangle_large_type_2_904af54a24fef1a287ea71bb0d95ecbe.png)
**線引きの基準は「権限と同意」**

今回の作業、AIと人間の分担はこうなりました。

**AI（Claude Code）に任せたこと**

- zenn-contentリポジトリの作成とpush

- 週1まとめ版への実装改修・dry-run検証

- SecretsへのZENN_REPO / ZENN_PAT登録と疎通テスト

- 作業記録のObsidianへの自動記録

**自分の手でやったこと**

- Zennへのアカウント登録（GitHubログイン）

- Zennダッシュボードでのリポジトリ連携

- Fine-grained PATの発行

並べてみると、線引きには理由があることに気づきます。

**「アカウントの作成」と「権限の付与」だけは、人間がやる**。
サービスの規約に同意するのも、トークンに権限を与えるのも、責任が伴う操作です。
ここをAIに丸投げするのは、楽とは別の話だと思っています。

逆に言うと、それ以外は全部任せられます。
リポジトリ作成もSecrets登録も、私は結果の報告を読んだだけでした。

**「どこ？」と聞ける相棒がいる安心感**

白状すると、PATの発行場所で迷子になったとき、私はAIに「どこ？」とだけ聞きました。
スクリーンショットを見せて、です。

返ってきたのは、正しいURLと画面のたどり方でした。
設定で迷ったとき、**今見ている画面ごと相談できる**のは、想像以上に作業が速くなります。

昔なら検索して、古い手順記事を引いて、画面が違って絶望するパターンです。
この「迷子タイム」が消えただけでも、セットアップの体感は大きく変わりました。

### 詰まったこと①：PATの発行場所で迷子になった
**リポジトリの設定画面を探し回った**

正直に書きます。
PATを発行しようとして、私は**リポジトリのSettings画面を開いて探し回りました**。

Collaborators、Webhooks、Deploy keys……。
それっぽい項目はあるのに、Fine-grained PATの発行ボタンがどこにもない。

正解は、リポジトリ側ではなく**個人アカウント側の設定**でした。

📌 右上の自分のアイコン → Settings → 最下部の **Developer settings** → **Personal access tokens** → **Fine-grained tokens**

「リポジトリに対する権限だから、リポジトリの設定にあるはず」という思い込みが敗因です。
同じ場所で迷う人は多いと思うので、先に書いておきます。

**権限は「絞るほど安心」**

Fine-grained PATの良いところは、影響範囲を細かく絞れることです。

万一トークンが漏れても、被害は zenn-content リポジトリの中身だけ。
他のリポジトリには一切触れません。
自動化でトークンを預ける以上、**「漏れても痛くない設計」**にしておくのが精神衛生上いいです。

### 詰まったこと②：Windowsの文字コードに最後まで絡まれる
**dry-runで突然の例外**

投稿前に、ローカルで変換結果を確認できるdry-runモードを用意してあります。
実行したら、いきなりエラーが出ました。

```
'cp932' codec can't encode character '\U0001f4e1' ...
```
犯人は、frontmatterに入れた絵文字（📡）でした。
Windowsのコンソールが日本語環境だとcp932で動いていて、絵文字を表示できなかったんです。

**実害はゼロ。でも心臓に悪い**

落ち着いて確認すると、**プレビューファイル自体は正常に生成されていました**。
失敗したのは「コンソールに内容を表示する」部分だけ。

本番のGitHub ActionsはUbuntuで動くので、文字コードはUTF-8です。
つまり本番には一切影響しません。

Windowsで日本語×自動化をやっていると、この手の「表示だけ事故」によく遭います。
エラーを見た瞬間に慌てず、**実体のファイルがどうなっているかを先に確認する**のがおすすめです。

### できあがった仕組みの全体像
最終的に、投稿パイプラインはこうなりました。

- **毎朝**: noteに当日のランキング記事を自動投稿（従来どおり）

- **毎週月曜の朝**: データベースから直近7日分を集計 → 週刊まとめMarkdownを生成 → zenn-content へpush → Zennが自動公開

地味に気に入っているのが、安全側に倒した設計です。

- Zenn側の処理が失敗しても、**noteの投稿は絶対に止めない**（独立ステップ・常に正常終了）

- Secretsが未設定の間は、何もせずスキップ（設定した瞬間から動き出す）

**追加コストは、ほぼゼロ円**

ランニングコストも書いておきます。

- Zennの利用料: **0円**

- GitHubのリポジトリとActions: **0円**（無料枠内）

- リード文リライトのAPI代: 週1回・数百トークンなので誤差レベル

入口を1つ増やすのに、固定費はほぼ増えていません。
X連携を見送った判断のときは「月45円＋管理コスト」が引っかかりました。
それと比べても、Zennは「置いておくだけならタダ」なのが気楽です。

**「朝7時公開」が朝8時になる話**

1つだけ、知っておくと精神衛生に良い小ネタを。

GitHub Actionsの定時実行（cron）は、**指定時刻ぴったりには動きません**。
混雑状況によって、平気で1〜2時間遅れます。

毎朝のnote投稿も、6時設定で実際の公開は7時台後半が多いです。
月曜のZenn記事も「朝のどこか」くらいの気持ちで待つことにしています。
ここで律儀に戦うより、受け入れて設計したほうが楽です。

✅ dry-runで確認した今週分は、TOP9・1位はスコア78点でした。
あとは月曜の朝を待つだけです。

### 初回記事の中身を、少しだけ先にお見せします
**1位はスコア78点の「自分にインタビューするAI」**

dry-runで生成された初回の週刊記事から、1位だけ紹介します。

今週の1位は「21-day-self-interview」というリポジトリでした。
**21日間、毎晩AIが3つの深い質問を投げかけてくる**セルフインタビューツールです。
ユーザーの言葉を記憶して、次の質問に反映していくのが特徴です。

私のパイプラインのAIは、これを100点満点中78点と採点しました。
評価コメントには「メンタルヘルス×AI×ジャーナリングの新しい組み合わせ」とあります。

正直、自分では絶対に見つけられなかったリポジトリです。
毎日GitHubを巡回するのはAIで、私は朝、結果だけ読む。
この分業があるから、週刊まとめ記事も「選定ゼロ秒」で作れます。

**今週は「当たり週」ではなかった**

包み隠さず書くと、今週のスコアは全体的に低めでした。
普段なら85点超えの「当たり案件」が出る週もありますが、今週の最高は78点。
2位以下は72点が横並びです。

それでも記事として成立するのは、ランキング形式の強みです。
「今週は不作でした」も、続けて見ている読者には情報になります。

### 効果はどうやって測るのか
**見る数字は2つだけ**

せっかく入口を作っても、効果を測らなければ意味がありません。
私のパイプラインは、noteの**フォロワー数とスキ数を毎日自動で記録**しています。

見るのはシンプルに2つです。

1. **Zenn側の閲覧数**（Zennのダッシュボードで確認）
2. **noteのフォロワー数の伸び**（月曜の投稿後に変化があるか）

Zennの記事末尾には、noteのマガジンへのリンクを1つだけ置いています。
「Zennで知る → noteを覗く → フォローする」の動線が機能するかの検証です。

**数字が出なかったら、それも書きます**

このシリーズの方針として、うまくいかなかった結果も公開します。
週1のまとめ記事で流入が増えなければ、頻度や構成を変えて再検証です。

### 再現したい人向け：最短チェックリスト
自分の環境でやってみたい人のために、手順を一覧にしておきます。

1. ✅ GitHubに公開リポジトリ zenn-content を作る（articles/ フォルダだけでOK）
2. ✅ ZennにGitHubアカウントで登録 → ダッシュボードからリポジトリを連携
3. ✅ Fine-grained PATを発行（**個人のDeveloper settings**から。対象1リポ・Contents RWのみ）
4. ✅ 投稿処理を動かすリポジトリのSecretsに ZENN_REPO と ZENN_PAT を登録
5. ✅ frontmatter付きMarkdownを articles/ にpushする処理を、自分のパイプラインに追加

注意点は2つだけです。

- PATの発行場所は**リポジトリ設定ではない**（私はここで迷いました）

- 自動生成記事を流すなら、**頻度はプラットフォームの文化に合わせる**（Zennなら週1まとめ推奨）

手動運用の人でも、1と2だけやれば「pushで公開」は使えます。
ローカルで書いてgit pushするだけでも、Zennの編集画面より楽かもしれません。

### まとめ：書く場所を増やしても、書く時間は増やさない
今回やったことを整理します。

- ✅ Zennの「GitHubからのデプロイ」連携で、push＝公開の仕組みを確保

- ✅ 毎日ではなく**週1のまとめ記事**に絞った（文化に合わせた頻度設計）

- ✅ リード文のAIリライトなど、重複コンテンツ対策を3つ実装

- ✅ 手作業は4ステップ・15分（リポジトリ作成とSecrets登録はAIが代行）

- ✅ PATは最小権限（対象1リポジトリ・Contentsのみ）で発行

書く場所は2つに増えましたが、私の作業は1秒も増えていません。
